# Подготовка к матчу

`essence` тратится здесь, до симуляции. Один и тот же пул идёт на характеристики и на крафт заклинаний. В бою каст идёт по уже собранным `SpellData`, повторного списания нет.

Бюджет на игрока: `PrepRules.START_ESSENCE = 100`. Полные потолки статов и заклинаний вместе в этот бюджет не помещаются: игрок выбирает, что купить.

## Когда открывается

После успешного старта пира грузится `res://scenes/prep/prep.tscn`, не `Game`.

| Кто | Кнопка |
|---|---|
| Одиночка и хост | `prep.start` |
| Клиент | `prep.ready` |

Хост запускает матч, когда каждый подключённый пир уже прислал сборку и сервер её принял. До этого кнопка старта выключена и показывает `prep.waiting`. В одиночной игре пир один, старт доступен сразу после собственной принятой сборки.

Клиент, подключившийся после перехода хоста в `Game`, в матч на этом этапе не входит. Сервер рвёт такое соединение, клиент остаётся в меню с `menu.status.connection_failed`.

## Дерево сцены `Prep.tscn`

```

        │   ├── LmbSlot
        │   ├── RmbSlot
        │   └── MmbSlot
        └── SideColumn (VBoxContainer)
            ├── StatusLabel (Label)
            ├── ConfirmButton (Button)
            └── SettingsButton (Button)
```

Ряд стата уже в сцене: название, текущее значение, цена следующей покупки, кнопка «+». Слот заклинания: два `OptionButton` (элемент и форма) и пять рядов параметров (урон, размер, дальность, длительность, прочность). Ряд параметра активен только у тех форм, которые это поле читают. Список форм и элементов — в [spells.md](spells.md). Пустой слот параметры не покупает.

Узлы рядов скрипт не создаёт. Тексты — ключи из [settings.md](settings.md).

## Черновик

На экране живёт черновик, не узел игрока:

```gdscript
var stats: PlayerStats            # duplicate дефолтного .tres, essence = START_ESSENCE
var slots: Array[SpellSlotDraft]  # длина 3

class SpellSlotDraft:
    var element: int = -1         # SpellData.Element, -1 = пусто
    var form: int = -1            # SpellData.Form, -1 = пусто
    var power_rank: int
    var area_rank: int
    var cast_range_rank: int
    var duration_rank: int
    var object_hp_rank: int
```

«+» у характеристики вызывает соответствующий `try_upgrade_*` у этого `stats`. Не хватило `essence` или параметр уже на потолке — черновик не меняется.

«+» у параметра заклинания вызывает `PrepRules.try_upgrade_spell(stats, draft, channel)`. Списание идёт тем же `stats.try_spend`.

Смена формы слота:

- оба списка на `prep.empty` (`-1`) — ранги обнуляются, стоимость установки и рангов возвращается в `stats.essence`;
- новая форма — прежняя стоимость слота возвращается, ранги обнуляются, затем `try_spend` цены установки этой формы;
- смена только элемента ранги и essence не трогает.

Цены установки: снаряд `0`, на себя `10`, область `15`, луч `15`, вокруг себя `15`, стена `20`, мина `20`. Форма без пары-элемента в сборку не уходит: оба поля либо `-1`, либо валидный индекс.

Возврат считает стоимость заново по тем же формулам, отдельный журнал трат не хранится.

## Проверка на сервере

Клиент шлёт ранги на `NetworkManager`, не готовые числа урона и не свой остаток `essence`:

```gdscript
# stat_ranks: speed, stamina, dash, vision, hp — пять int
# elements, forms: по 3 int, -1 = пустой слот
# spell_ranks: 15 int, по пять на слот, порядок полей как в SpellSlotDraft
@rpc("any_peer", "reliable")
func submit_loadout(stat_ranks: PackedInt32Array, elements: PackedInt32Array, forms: PackedInt32Array, spell_ranks: PackedInt32Array) -> void
```

Сервер принимает RPC до старта матча и только от пира, который ещё не помечен готовым. Дальше собирает пул с `START_ESSENCE` на свежей копии `player_stats_default.tres`:

1. Повторяет `try_upgrade_*` ровно `rank` раз для каждого стата.
2. Для каждого слота ставит элемент и форму. Пара `-1/-1` даёт пустой слот. Один `-1` при втором валидном индексе, индекс вне enum или ранг поля, которое форма не читает, отклоняет сборку.
3. Повторяет апгрейды параметров с базы этой формы.
4. Любой `false` или отрицательный ранг отклоняет сборку.
5. Успех запоминает копию `PlayerStats` и три `SpellData` за этим peer id.

Отклонение уходит владельцу сигналом на его экран (`prep.rejected`). В матч эти числа не попадают.

Хост прогоняет свою сборку той же функцией локально.

`Game.spawn_player` перед `add_child` записывает в игрока уже принятые `stats` и три слота. `current_hp = max_hp`, `current_stamina = max_stamina`.

## Характеристики

Цены и потолки — в [player-stats.md](player-stats.md). На этом экране покупаются все пять: скорость, выносливость, сила рывка, обзор, здоровье.

## Крафт заклинаний

Сервер копирует `spell_base.tres`, записывает элемент и форму и подставляет базу чисел этой формы из [spells.md](spells.md). Ранги поднимают уже эти числа.

| Параметр | Шаг | Базовая цена | Рост | Потолок ранга | Какие формы |
|---|---|---|---|---|---|
| `power` | `+2` | `8` | `+4` | `5` | все, кроме стены |
| `area` | `+0.25` | `8` | `+4` | `4` | снаряд, область, стена, вокруг себя, мина |
| `cast_range` | `+40` | `6` | `+3` | `5` | снаряд, область, стена, луч, мина |
| `duration` | `+0.5` сек | `6` | `+3` | `4` | снаряд, область, стена, мина |
| `object_hp` | `+20` | `8` | `+4` | `5` | стена и мина |

Цена ранга: `base + rank * growth`. У стены `power` не покупается: стена блокирует и держит `object_hp`, нагрузку элемента не выпускает. У света `power` — величина лечения, шаг тот же.

Пять рангов урона у снаряда с базой `10` дают `power 20`. Пять рангов прочности у стены с базой `60` дают `object_hp 160`.

Поведение в матче описано в [spells.md](spells.md). Сервер читает уже посчитанные `element`, `form`, `power`, `area`, `cast_range`, `duration`, `object_hp`.
